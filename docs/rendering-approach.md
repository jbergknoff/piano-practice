# Sheet Music Rendering Approach

## Why not OpenSheetMusicDisplay?

OSMD was the initial choice because it handles the full MusicXML 3.1 spec with zero effort — pass in a string, get back a rendered score. The problem is that it renders into an opaque SVG subtree with no map from logical notes to SVG elements. After `render()` returns there is no stable way to find "the notehead for measure 3, beat 2" and change its color. Any post-hoc DOM queries are fragile (class names are internal), and re-rendering on every color change resets all manual edits. OSMD also weighs in at several MB bundled.

## Why not wrap VexFlow declaratively?

VexFlow's rendering model is deeply imperative: you construct `Stave`, `StaveNote`, and `Voice` objects, call `Formatter.format()`, then call `draw()` — which mutates a canvas or SVG element as a side effect. There is no virtual-DOM representation to diff. Wrapping this in React/Preact would require reimplementing reconciliation for VexFlow objects, and the result would be fragile because VexFlow's internal layout depends on cumulative state. No maintained declarative wrapper exists that handles real musical notation.

## Why building from scratch is tractable here

A general-purpose notation renderer (Sibelius, Finale, LilyPond) takes years. But the MusicXML our generator produces is a narrow subset:

- One staff per part, with multiple parts stacked (e.g. treble + bass) and horizontally aligned by a shared rhythm spine
- Five note types: whole, half, quarter, eighth, 16th (with dotted variants)
- Chords (simultaneous notes on one stem), beamed eighth/16th groups
- No grace notes, no multi-voice, no ornaments, no dynamics
- Accidentals as sharps, plus naturals to cancel an earlier sharp in the bar (never flats)

That subset is a few hundred lines of SVG-producing Preact components.

## What we built

`SheetMusicDisplay` is a pure Preact component. It takes a MusicXML string, parses it into a typed data structure, computes layout geometry, and renders an `<svg>` whose structure mirrors the MusicXML hierarchy:

```
Score → Part[] → Measure[] → (ChordGroup | Rest)[]
  ↓        ↓         ↓              ↓
<svg>  <Staff>  <Measure>    <ChordGroupEl> / <RestEl>
```

Every notehead is a SMuFL glyph (a `<text>` element set in the Bravura music font) with a stable, autogenerated ID:

```
p{partIndex}-m{measureNumber}-n{noteIndex}-v{voiceIndex}
```

IDs are deterministic from the MusicXML structure. To highlight a note, pass `noteColors={{ "p0-m3-n1-v0": "red" }}`. A dedicated overlay layer (`NoteColorOverlay`) draws colored copies of just those glyphs on top of the black notes, so a color change re-renders a handful of glyphs instead of the whole score.

## Trade-offs

- **We own the rendering code.** Musical edge cases (grace notes, multi-voice, tie slurs, complex accidental rules) need to be added explicitly. The current scope covers what the MIDI-to-MusicXML generator actually produces.
- **Beaming is implemented.** Consecutive eighth/16th notes within a beat are grouped under beams (`groupBeamableEvents` + `beamStemOverrides`), with stem directions and beam angles resolved per group.
- **Ties are parsed but not rendered.** Tie information is preserved in the data model (and drives playback duration), but no tie slur is drawn yet.
- **The Bravura music font is bundled.** All notation — noteheads, accidentals, clefs, rests — is drawn with SMuFL glyphs from Bravura (`@fontsource/bravura`, OFL license), so rendering is consistent across platforms instead of depending on whatever music font the OS provides.

## Cursor and scroll

The playback cursor is an absolutely-positioned `<div>` (a sibling of the staves) moved horizontally with `transform: translateX(cursorX)`. Keeping it out of the SVG means the 60fps position updates during playback never re-render the note tree: an rAF loop reads the live beat and writes the transform directly.

`cursorX` comes from `computeCursorX(beat, score, layout)`, a pure function. Given a beat (in quarter notes) it finds the containing measure and walks that measure's **rhythm spine** — the shared per-measure grid of onset divisions that aligns notes across staves (see `buildMeasureSpine`) — interpolating linearly between the two onset anchors that straddle the beat, so the cursor moves continuously rather than jumping note-to-note.

One subtlety: a measure's first note is *not* at the barline — the clef/key-signature/padding lead-in sits to its left. So the cursor anchors a measure's downbeat to the **first notehead's x**, not the barline, and treats that lead-in as space the cursor sweeps during the *previous* measure's final beat. This keeps the cursor glued to the notes on every downbeat while staying continuous across barlines. (Anchoring the downbeat to the barline was a bug: the correctly-highlighted downbeat notes appeared offset to the cursor's right.)

### Scroll following

The scroll container (`<div style="overflow-x: auto">`) is driven by a `useEffect` that fires whenever `cursorX` changes:

- **Smooth follow** (incremental beat changes during playback): an easing RAF loop moves `scrollLeft` by 12% of the remaining distance each frame, keeping the cursor centered without jarring jumps.
- **Instant snap** (reset, seek, mode change): the caller sets `snapPendingRef.current = true` before changing the beat. The effect sees this flag on its first run after the re-render, skips the animation, sets `scrollLeft` directly, and clears the flag.
- **Detached** (user scrolled manually): a `detachedRef` boolean is set `true` by pointer-drag or wheel events. While detached the smooth-follow effect returns early. It re-attaches automatically when the cursor drifts back into the visible viewport, or immediately on any instant snap.

The `snapPendingRef` flag is set by `setCursor(beat, "jump")` in `PracticeScreen.tsx` and consumed (and cleared) by `SheetMusicDisplay` — there is no function call crossing the component boundary, just a shared ref.

## Future extension: ad-hoc note overlay

The `<svg>` is a plain DOM element. A future `overlayNotes` prop could render a second `<g>` layer of noteheads at approximate beat positions, computed from a beat offset rather than the measure layout. This would let the app show live-played notes against the sheet music for comparison — the same coordinate math applies.
